# Common independent review brief

Review the current shared working copy of PSLocalBase on main, HEAD d6b5e537bf7b9aee83ee8fb092f0c5615e2b6b2a, version 2.1.0, INCLUDING the pending documentation/help edits and DOCUMENTATION-AUDIT.md. Do not evaluate HEAD alone. Baseline hashes are in baseline-sha256.csv. Do not modify production files, docs, tests, or git state. Write only your assigned review report in this directory; use unique temporary paths for runtime probes.

This repeats the six historical areas: Security, Code Quality, Functionality/Data Integrity, Architecture, Documentation, Test Adequacy. Each provider has three independent specialist reviews covering two areas each. Do the review yourself; do not spawn or delegate further. The coordinator executes the complete 22-suite runner on PS7 and PS5.1, both Playground automation checks, manifest/static analysis, documentation checks, and packaging. Do not duplicate the full runner; inspect tests and run targeted independent probes of risks/edge cases. Do not publish/upload or modify user data. Local code is authoritative.

Use fresh scores out of 100, independently of historical scores. For each assigned area provide a score, strengths with file:line evidence, explicit reasons for deductions and whether they represent a confirmed defect, accepted design tradeoff, or evidence gap. Suggested interpretation: 90-100 strong implementation with limited defects/gaps; 80-89 material weaknesses with usable core; 70-79 substantial limitations; below70 serious deficiencies. Scores are review judgments, never measured coverage or certification. Perfect scores need explicit justification and do not imply absence of defects.

Every finding needs severity (critical/high/medium/low/informational), file/line, concrete trigger or reproduction, observed vs expected behavior, impact and recommendation. Separate confirmed issues from hypotheses. Report tests actually run with edition/version, command or reproducible probe, outcomes and limits. Explicitly discuss accepted numeric comparison limits, guarded expression-index performance, materialized reads, Windows-only/native DLL assumptions where relevant. Do not treat documented accepted tradeoffs as new defects unless contradictory behavior is demonstrated.

Use report sections: Identity and scope; Findings; Scores (two rows, with deductions); Validation executed; Limits and objections. State exact provider/model/effort supplied by your assignment. Historical reports are context, not proof of the current state. Preserve independently reasoned scores; the coordinator will consolidate both providers in one table across all six areas, plus historical columns with provenance and N/A for historically unscored areas.
